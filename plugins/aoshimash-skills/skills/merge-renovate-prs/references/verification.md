## The core distinction: merged ≠ deployed ≠ working

"Merged the PR and CI is green" is not "the change is live and the system is healthy." Three separate states must each be confirmed:

1. **Merged** — the change is in Git. (Easy; the PR's merged state confirms it — with the CLI, `gh pr view`.)
2. **Deployed / applied** — the change reached the running system: a GitOps controller reconciled it, CI deployed it, or a manual apply ran. In GitOps repos this is **asynchronous** — the merge returns instantly but Flux/Argo may take minutes to reconcile.
3. **Functioning** — the system is actually healthy after the change: health checks pass, the app responds, no regression appeared.

A "post-merge check passed" that only confirmed state 1 (or even 2) is a false sense of done. The 2026-05-04 outage looked "merged and applied" while the cluster was cascading into failure. In autonomous mode this distinction carries the whole safety story: the post-merge verification is what replaced the human approval, so cutting it short is not an optimization — it is removing the brakes.

## Three-state verification

For each PR, after merge and after running any A/B/C apply:

### V-1: Confirm merged

Confirm the PR is merged and the expected commit is on the default branch.

### V-2: Confirm deployed/applied (async-wait)

Confirm the change reached the environment. This depends on the deploy mechanism from Phase 0:

- **GitOps (Flux/Argo):** poll the controller until it reports the new revision reconciled — do **not** assume reconcile is instant. Wait for the reconcile to complete (or the controller's healthy/synced status), with a sane timeout. If it does not reconcile, that is a failure, not "give it more time forever".
- **CI deploy:** confirm the deploy job ran and succeeded.
- **Manual apply (B/C):** confirm the apply command's output indicates success, or the user confirmed the C step.

### V-3: Confirm functioning (health + regression)

Confirm the system is healthy *because of and despite* the change:

- Run the checks from the **verification plan** assembled in Phase 0-4 — the human-supplied checks (user request, repo runbooks/docs) plus the repo-type baseline (pods Ready at expected replica count, endpoints responding, the upgraded component reporting the new version, etc.). Do not substitute weaker checks for ones a human defined, and do not invent sufficiency the plan does not claim.
- **Regression check:** confirm nothing that worked before is now broken — not just that the upgraded component is up. An upgrade can be "applied successfully" and still break a dependent service.
- Wait for transient states to settle (rolling restarts, leader elections) before judging health. For changes classified **disruptive** (see below), use an extended settle window.

Only when V-3 passes is the PR done. Then proceed (workflow.md 2-9). The one exception is an artifact whose publish is gated behind a separate trigger, which has no V-3 yet — see [Gated publish](#gated-publish-merged-is-not-shipped).

## Adapting verification to the repo type

The three states are universal; what implements V-2/V-3 differs by what the repo ships. Phase 0's deploy-mechanism discovery tells you which row applies:

| Repo type | V-2 (applied) | V-3 (functioning) |
|---|---|---|
| **GitOps** (Flux/Argo → cluster) | Controller reports the new revision reconciled/synced. | Workloads Ready at expected counts, endpoints respond, upgraded component reports the new version, no regression in dependents. |
| **CI-deploy app** (merge to main triggers deploy) | The post-merge deploy workflow on the default branch succeeded. | The deployed service's health checks / smoke tests pass; monitoring shows no regression. |
| **Library / no deploy** (e.g. an npm package repo where merge ships nothing) | The post-merge workflow (build + full test suite) on the default branch succeeded. | Nothing beyond V-2 exists to observe — the default-branch CI **is** the functioning check. Do not invent one; do not skip waiting for it either. The PR's own green CI is *not* a substitute: verify the suite on the merged default branch. |
| **Artifact with gated publish** (the repo builds a container image or package, and its CI, as far as recognition can see, publishes it only on a trigger separate from the merge — a version tag, a manual workflow dispatch, a release; consumers, if any, reference a published version) | **No deployment is expected, and none is waited for.** Confirm the default branch holds the change, the artifact-build job — the one that builds without publishing — succeeded on the merged default branch, and **no run of any workflow that publishes the artifact started at or after the merge** — one read for each publishing workflow recognition enumerated, not just the release workflow. Take those reads only once the merge's runs have **settled**, on positive evidence: every workflow the merge is expected to start has a run on the merge commit, and every run there has completed. An empty or partial result is not settled — GitHub creates runs asynchronously after the merge, so it can mean "not created yet" — and an expected run that does not appear within the wait V-2 allows is verification that cannot be completed. Settling gives a slower workflow the merge started its chance to dispatch or tag; then each publish-run read must return no rows — one row is enough to fail it, so no truncation check applies (all reads: [platform-github.md](platform-github.md) "Workflow runs (gated-publish V-2)"). A publish run there means the merge reached the trigger after all: stop the line and escalate to the human with the run, since a revert PR does not unpublish it. The check sees only GitHub Actions runs, and only those that exist when it reads: a publish started later — at a schedule's next tick, after another workflow completes, or by automation outside the repository — escapes it, and so does a publish by any CI or build service other than GitHub Actions. Recognition is what rules out the paths its listings find in the repository; a publisher configured outside the repository, or in a file those listings do not match, is a known limit of both (below). The check is a backstop over the Actions runs the merge itself started, not a guarantee. Where the build job runs only on pull requests, there is no post-merge build to observe: V-2 is then V-1, the publish-run check and 2-3's CI gate, and adds nothing beyond them — say so in the report, and put "the merged tree has not been built" in the follow-up. Do not wait for a reconcile or deploy job: none will run. | **Does not exist yet.** The change was not published by the repository's CI, as far as the run can see, so there is no new published artifact whose functioning could be checked. Do not invent a V-3, and do not substitute the build job for one. The PR is done at V-2 but is **not** "merged & verified": it always leaves a follow-up (below). |

This is why autonomous mode's Phase 0 precondition is stated as *observability*, not "cluster access": for a library repo, being able to read post-merge workflow results on the default branch is sufficient observability. The same holds for the gated-publish row.

### Gated publish: merged is not shipped

The gated-publish row is the one where merged ≠ deployed ≠ working bites hardest, because every state the run can check comes back clean while the change has not been published by the repository's CI, as far as the run can see. It differs from the library row in that something downstream exists — the registry and the consumers — and, unless something outside what recognition reads published the change, it keeps the previous artifact, indefinitely, until someone acts.

- **Recognize it in Phase 0 (workflow.md 0-1) — only on positive evidence.** All three of these must hold:
  1. **Every workflow that publishes the artifact triggers only on a deliberate trigger.** Enumerate **every** workflow file in the default branch's `.github/workflows/` — a complete listing ([platform-github.md](platform-github.md) "Workflow files (gated-publish recognition)") — and read each one: a workflow publishes the artifact when any of its jobs pushes it to a registry — any registry, not only the one its consumers are known to pull from — directly or through a reusable workflow or action. A repo can publish the same artifact from more than one workflow — a gated release workflow beside a `ci.yml` that pushes `:main` or `:edge` tags on every push to `main` — so the release workflow alone settles nothing. Each publishing workflow must trigger **only** on `push: tags` (a `push` trigger with `tags` or `tags-ignore` and no `branches` or `branches-ignore`), `release` or `workflow_dispatch` — a closed list. One publishing workflow with any other trigger — a push to the default branch, `schedule`, `workflow_run`, `repository_dispatch` (GitHub offers no way to send it but the API, and its senders are usually automation, often outside the repository, so it is no evidence of a human act), or anything not in the list — means this is not the row. So does a listing that may be incomplete, a workflow file that cannot be read, a workflow whose publishing you cannot determine (a step, reusable workflow or action whose effect you cannot read), or finding no publishing workflow at all: an unknown publish path is not a gated one. The one trigger judged differently is `workflow_call`: a reusable workflow has no trigger of its own to judge, so it is judged by its callers. Find every enumerated workflow with a job that `uses:` it (by its local path or by this repository's path at a ref); each caller publishes the artifact through it and must itself satisfy this condition, and the callee's other triggers, if any, must be on the list. A call runs the callee at the ref it names, which need not be the copy enumerated here: `./.github/workflows/x.yml` runs it from the caller's own commit, `{owner}/{repo}/.github/workflows/x.yml@{ref}` at `{ref}`. Read each workflow of this repository that a job calls at the ref its call runs it at (the contents read in [platform-github.md](platform-github.md), with that ref), and judge from that read what the caller does through it — publishing here, tagging, releasing or dispatching in (2); a callee that cannot be read at that ref is one whose effect you cannot determine, and the row does not apply. A `workflow_call` publishing workflow with no caller among the enumerated workflows — its callers, if any, are elsewhere — or one whose callers you cannot all identify, means this is not the row. A caller in another repository is outside the listing (known limit below).
  2. **Whatever reaches those triggers is itself started only by a deliberate human act.** In every workflow enumerated for (1), find each job that pushes or creates a tag a publishing workflow's `push: tags` filter matches (any tag, where you cannot evaluate the filter), creates a release, or dispatches a publishing workflow — directly or through a reusable workflow, action or script — for example semantic-release or a tag-on-merge job pushing the tag with a PAT or App token, a `closed` pull-request workflow that tags or dispatches when the PR merged, a nightly job that tags or dispatches, or a `push: main` workflow running `gh workflow run` (`workflow_dispatch` and `repository_dispatch` create runs even when sent with `GITHUB_TOKEN`). Each such workflow must itself trigger only on (1)'s closed list (with `workflow_call` judged by its callers, as there), and whatever reaches its trigger is held to the same test. One with any other trigger — a push to any branch, `schedule`, `workflow_run`, `repository_dispatch`, `pull_request` or `pull_request_target` of any type (a `types: [closed]` run, usually guarded by `github.event.pull_request.merged`, is on the PR's ref, not the merge commit, so V-2's settle read never sees it), `merge_group`, or anything not on the list — means this is not the row, and so does a job whose effect on tags, releases or dispatches you cannot determine (a token-holding step or script you cannot read). A release bot or external service the repo's docs name as tagging, releasing or dispatching rules the row out unless the docs show that only a human act starts it. Establish this from the workflow files enumerated for (1), the configuration read for (3), and the repo's docs.
  3. **Every CI or build configuration outside GitHub Actions publishes only on a deliberate trigger.** List the default branch's whole tree from a complete listing ([platform-github.md](platform-github.md) "CI and build configuration outside Actions") and look for other CI or build configuration — `.gitlab-ci.yml`, `.circleci/`, `Jenkinsfile`, `cloudbuild.yaml`, `.travis.yml`, `.drone.yml`, `azure-pipelines.yml`, `bitbucket-pipelines.yml`, `buildspec.yml`, `appveyor.yml`, `.buildkite/`, `.tekton/`, `.woodpecker/`, or any other at the repository root, named here or not. Read each one found. Every job, stage or step in it that publishes the artifact (to any registry), or that pushes a tag, creates a release or dispatches a workflow (1) gates, must be shown by the configuration itself — a condition on that job or stage, or the pipeline's own trigger definition — to run **solely** on a tag push or on a manual trigger a human starts. Any other trigger rules the row out: a push to a branch, a schedule, a merge or pull-request event, a trigger chained from another job or pipeline (an upstream job, a multi-project, parent or downstream pipeline, a trigger step), a trigger sent through an API or webhook (a pipeline trigger token — the analogue of `repository_dispatch`), or a trigger the configuration leaves to the service's settings or defaults — a configuration whose publishing job carries no such condition runs on whatever starts the pipeline, which the file does not show. So does a trigger you cannot determine, a listing that may be incomplete, or a file you cannot read or whose effect you cannot determine.

  Consumers, where any are located, reference the artifact by version or digest, in this repository or elsewhere; finding none does not rule the row out, and the follow-up says so. Where (1), (2) or (3) cannot be established — a step, reusable workflow or action whose effect you cannot read, a release tool the docs name, a token-holding job you cannot rule out, a reusable workflow whose callers you cannot all find, another CI's configuration you cannot read or whose publishing job's trigger it does not show — **this is not the row**: treat the merge as possibly publishing, so nothing below applies, and 0-4 judges the revert path as for any other mechanism. Decide per artifact the PR changes, not per repo: a repo can auto-deploy one target and gate another, and a PR touching both gets both rows — the other target's V-2 and V-3 still have to pass (workflow.md 2-9).

  **Known limit: a publisher configured outside the repository, or in a file the listings do not match.** Recognition reads what its listings find in the repository, so all it establishes is that **nothing in the CI configuration it found publishes the artifact on a merge** — not that the repository's CI, or anything else, does not. A publisher whose trigger lives in a service's own settings leaves nothing in the tree to read: a registry-side autobuild (Docker Hub automated builds, Quay build triggers), a CI service trigger with an inline build config, an external service that pushes a tag or sends a `workflow_dispatch` through the API when a pull request merges (recognition cannot tell that call from a human's), or a workflow in another repository that calls a reusable workflow of this one. Where the repo's docs name such a service, (2) rules the row out; where they do not, neither recognition nor V-2 — which reads GitHub Actions runs only — can rule it out or see its publish. Configuration below the root in a file the filter in (3) does not match is likewise missed: a CI system the filter does not name, or a named one kept under another name or path (microsoft/vscode keeps Azure Pipelines YAML under `build/azure-pipelines/`, and the listing returns none of it).
- **Re-judge it for a PR that changes what recognition read.** Recognition reads the default branch as Phase 0 found it, but a merge runs the PR's versions of the files it changes — and a `./.github/workflows/x.yml` call runs the callee at the merge commit. **Recognition's inputs** are every file it read or depends on: anything under `.github/workflows/`, a local action (an `action.yml` or `action.yaml` a `uses: ./…` reaches, directly or through another local action) or reusable workflow a `uses:` names, a script or other file read to judge a step's effect, a path (3)'s filter matches, and a root file read as CI or build configuration — workflow.md 2-4 and 2-9 use this definition. Phase 0's recognition therefore holds only while no merge has changed one of them: after a merge that changes one, recognize the row again on the default branch's new head before the next PR (workflow.md 2-9), and judge later PRs against that. **A re-recognition that no longer recognizes the row** — after this run's merge, or because a merge outside the run (a human's) changed the default branch — ends the row for the rest of the run. It is not a verification failure, so the line does not stop; but 0-4's revert-path judgement for the artifact rested on the row, so every remaining PR to that artifact, and every remaining PR that changes one of recognition's inputs, has no verified rollback path: autonomous mode defers each (workflow.md 2-5 condition 2) with that reason — as 0-3 excludes the PRs touching a drifted component — and interactive surfaces them. PRs to other targets continue. Report the lost recognition beside the merge that preceded it. **Known limit:** the run reads the default branch's current files only when it recognizes or re-judges, so a merge outside the run is seen only at the next such read; a PR that changes none of recognition's inputs is judged on the recognition the run holds. While the row is recognized in this repo, for any PR whose changed files ([platform-github.md](platform-github.md) "PR changed files (gated-publish re-judgement)") include one of recognition's inputs, whether or not it changes the artifact's own source, judge (1)–(3) again, before its merge and before the row is applied to it, on the tree that PR's merge would produce: the head's version of each file it changes (a removed file gone, a renamed one at its new path), the default branch's current version of the rest. A changed-file list that may be incomplete, a judgement that differs from the one the run holds, or one that cannot be made means **the row does not apply to that PR**: treat its merge as possibly publishing, as above. The run's revert-path judgement (0-4) rested on the row, not on this PR, so no rollback path is verified for it: autonomous mode defers it (workflow.md 2-5 condition 2), interactive surfaces it. Where the judgement holds, V-2's expected set for the PR comes from the re-judged enumeration, and a PR that does not change the artifact's own source — so is verified under another row — still takes V-2's publish-run reads after its merge, since its merge is what could start a publish. The judgement is pinned to the head it read: if the head moves before the merge, judge again (workflow.md 2-6).
  - **A changed external `uses:` ref in a file an ungated workflow executes rules the row out for that PR.** Re-judging re-reads this repository's files; it does not read the implementation of an action or reusable workflow from elsewhere (`uses: owner/action@ref`, `owner/repo/.github/workflows/x.yml@ref`, `docker://image:tag`), and a new ref runs code recognition never read — a build action whose new major pushes by default, or one that starts tagging. Such a ref sits in a workflow file or in a local composite action's `action.yml` / `action.yaml`, which runs inside whatever workflow reaches it; Renovate's github-actions manager updates both (its default `managerFilePatterns` match YAML under `.github/workflows/` and `.github/actions/`, and any `action.yml` / `action.yaml`). So for every workflow file and every `action.yml` / `action.yaml` the PR changes — wherever it sits, whether or not recognition read it — compare its external refs with the default branch's version. Where one changed, find every workflow that reaches that file, directly or through local actions and reusable workflows of this repository (by local path, or by this repository's path at a ref), among the enumerated workflows. The PR is not under the row, whatever the re-judgement found, unless every such workflow runs solely on (1)'s closed list (with `workflow_call` judged by its callers); one that does not, or a reaching set you cannot determine — a `uses:` path built from an expression, a local action or workflow you cannot read — rules it out. A changed file no enumerated workflow reaches runs nothing in this repository's CI. A ref changed only in files reached solely by workflows on that list does not rule it out: their trigger, read from this repository's file, still waits on a human act. The cost is real but bounded: of aoshimash/rx's 49 Renovate PRs, the 9 that touch `.github/workflows/` — all GitHub Actions updates, each changing a ref in a workflow run by pushes, pull requests or comments (`api-ci.yml`, `web-ci.yml`, `security-ci.yml`, or the since-removed `claude.yml` and `claude-code-review.yml`) — would defer, and the other 40 are unaffected; none of the 49 touches an `action.yml` or `.github/actions/`. **Known limit:** an external ref that moves upstream with no change here (a floating tag such as `@v6`) changes the code a workflow runs without any PR; neither this check nor recognition sees it.
- **It is not a manual-only deploy for 0-4's revert-path precondition.** Once recognized, a merge publishes nothing through the repository's CI as far as the run can see — recognition checks the configuration its listings find, within the limit above, and V-2's publish-run check backs it up over the Actions runs each merge starts — so a revert PR restores the source and, as far as the run can see, there is nothing else to undo. Observability is the default-branch workflow runs (the build job's, and each publishing workflow's run list), as for a library repo; where the build job runs only on pull requests, it is the PR check reads 2-3 already makes plus each publishing workflow's run list. Do not fall back to interactive mode for this row.
- **The publish and the consumers' pin bumps are not this PR's work.** They are the artifact's release: the trigger is deliberately separate from the merge, so merging without them creates no drift, and they are not classified A/B/C (workflow.md 2-4). The agent never fires the publish trigger or bumps a consumer's pin, even where a runbook or Renovate note describes the step: a published version is not undone by a revert PR, so running it would leave the run without the rollback path its merges depend on. Those steps go in the follow-up, for a human.
- **The follow-up is mandatory.** For every PR this row covers, record what reaching the running system still takes and who does it: fire the publish trigger (name it — the tag pattern, the workflow to dispatch, or the release to create), then bump each consumer's pin (name the consumers found, or say none were located). "Who" is the role or document the repo names for releasing, else a maintainer. It goes on the PR (workflow.md 2-8) and in the report's own category (3-1).

## Harmless residue vs. real failure

After disruptive changes (especially reboots), the system often shows **alarming-but-harmless residue**. Misreading it either way is bad: panicking over residue causes needless reverts; dismissing a real failure as residue ships an outage. Distinguish deliberately:

| Looks alarming | Likely harmless residue when… | Likely real failure when… |
|---|---|---|
| `Failed`-phase pods after a node reboot | Their controller (Deployment/DaemonSet/StatefulSet) is **already at full Ready count** — the `Failed` pods are stale replicas from before the reboot that the scheduler hasn't garbage-collected. | The controller is **not** at its desired Ready count, or new pods keep entering `Failed`. |
| Pods restarting | A one-time restart during a rolling update that then stays `Running`/`Ready`. | `CrashLoopBackOff` — restart count climbing, never reaching `Ready`. |
| Brief endpoint errors | Errors only during the rollout window, clearing once pods are Ready. | Errors persisting after the rollout settled. |

The deciding question is usually: **is the controller at its desired ready state, and is the residue static (not growing)?** If yes, it is residue — note it and move on. If the failure indicators are live and growing, it is real — go to failure handling. When you genuinely cannot tell, **fail closed**: treat it as a real failure. (In autonomous mode, fail-closed means an auto-revert — a needless revert of a healthy change is recoverable; a dismissed outage is not.)

## Downtime classification

Classify every change's disruption. The classification is used differently per mode (workflow.md 2-5):

| Class | Examples | Autonomous | Interactive |
|---|---|---|---|
| **Non-disruptive** | Rolling update with surge, multi-replica deployment, additive config. | Proceed normally. | Normal approval. |
| **Disruptive** | Node reboot (Talos/OS upgrade), single-replica restart, DB failover, control-plane disruption, CNI restart affecting networking. | **Not a gate** — proceed, but: use an extended settle window in V-3, respect any timing constraint the user gave (defer if it cannot be honored now), and flag the change prominently in the final report. | **Prominent, explicit downtime confirmation** spelling out blast radius + expected downtime + maintenance-window timing — even if the plan was batch-approved. |

When in doubt about whether a change reboots a node or restarts a singleton, treat it as disruptive.

## Rollback-readiness check (a merge precondition in autonomous mode)

Before merging (autonomous) or before any irreversible/disruptive apply (interactive), confirm a rollback path actually exists — *before* pulling the trigger, not after it fails. Match the path to the change:

| Change | Rollback path to confirm |
|---|---|
| App/manifest change (GitOps) | A **revert PR** restores the prior state, and the controller will reconcile it. |
| App change (CI deploy) | A **revert PR** redeploys the prior version via the pipeline. |
| Library dependency bump | A **revert PR** restores the prior lockfile/manifest. (Trivially true; the check is quick.) |
| Artifact with gated publish (source of an image or package published on a separate trigger) | A **revert PR** restores the source. As far as the run can see, the repository's CI published nothing on the merge, so nothing else needs undoing. That rests on recognition (no automatic path in the CI configuration its listings find leads from a merge to the publish) and on the agent never firing the trigger ([Gated publish](#gated-publish-merged-is-not-shipped)); a publisher configured outside the repository, such as a registry-side autobuild, is a known limit recognition cannot rule out. V-2's publish-run check catches a path recognition missed only among the GitHub Actions runs the merge started, and escalates, since a revert PR does not unpublish — a publish a schedule, later automation or another CI service fires is outside its view ([Gated publish](#gated-publish-merged-is-not-shipped)). |
| Helm release (B-class apply) | `helm rollback` to the prior revision is available. |
| etcd / control-plane mutation | A current **etcd snapshot** exists. |
| Node OS / kernel | An **A/B partition** or prior image is available to boot back into. |
| Database migration | A **backup** taken immediately before, and the migration is reversible (or a down-migration exists). |

Mode difference:

- **Autonomous:** a verified rollback path is a **merge precondition**. Revert-PR-based paths are usually verifiable from Phase 0's deploy mechanism alone; the non-git paths (snapshot, A/B partition, backup) must be confirmed to exist for the specific change. **No verified path → defer the PR unmerged** (workflow.md 2-5). Additionally, for B-class applies, identify the **inverse operation** before running the forward one — if no safe inverse exists and no other path covers it, defer.
- **Interactive:** if no rollback path exists for an irreversible change, **say so at the approval gate** — that materially changes the risk and the user may choose to defer or to create a rollback path first.

## Failure handling: auto-revert (autonomous) / stop-the-line (interactive)

Entered from workflow.md 2-9 when an apply or verification fails, or residue resolves to a real failure. In both modes the serial discipline is why this works: the failure maps to exactly one change, so the revert target is unambiguous.

### Autonomous: auto-revert procedure

1. **Revert in Git.** Create a revert PR for the merged change (see [platform-github.md](platform-github.md) for the commands, including the merge-method-dependent revert form), approve it, and merge it. Do not wait for the bot or a human — this is the pre-verified rollback path being exercised.
2. **Undo any B-class apply.** If a manual apply ran (2-7), execute the inverse operation identified during the rollback-readiness check (e.g. `helm rollback`). Order matters: revert Git first so a GitOps controller does not re-apply the bad version over your rollback.
3. **Verify the recovery.** Re-run the full three-state verification on the *reverted* state: revert merged → reconciled/deployed → system functioning again. A revert that has not been verified is just another unverified change.
4. **Document and stop the line.** Post the mandatory revert comment on the original PR (what failed, what was reverted, recovery state, link to the revert PR — workflow.md 2-8). Then stop processing further PRs this run, even though recovery succeeded: one verification failure means the pre-check missed something, and the remaining queue deserves human eyes before the automation continues. Report per Phase 3.
5. **Escalate when the revert path fails.** If the revert PR cannot be created or merged, the inverse apply errors, or the recovery verification does not pass: **stop immediately and escalate to the human** with the full state — what was merged, what failed, what was attempted, what the system looks like now. Do not retry destructive operations in a loop. Do not attempt creative alternative recoveries unprompted. This is the one place autonomous mode always comes back to a person.

### Interactive: stop-the-line

1. **Stop.** Do **not** proceed to the next PR. The serial discipline exists precisely so that a failure is isolated to one change; carrying on would compound it (the 2026-05-04 lesson).
2. **Surface** the problem clearly: what was applied, what failed, what the current state is.
3. **Offer rollback** using the path confirmed at the approval gate. Present it as a proposal (rollback is itself a mutating action that needs approval), with the steps.
4. **Get user direction** — roll back, investigate together, or hold.
5. **Fail closed when uncertain.** If you cannot determine whether the change is working, do not optimistically continue. Treat unknown as failed and stop.

Never fabricate a passing result to keep the loop moving. A truthful "this failed, here is the state, here is what was reverted (or the rollback proposal)" is the correct output.
